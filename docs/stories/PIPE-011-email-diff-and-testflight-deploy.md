# PIPE-011: Show Fix Diff in Email + Approve-to-TestFlight

**Priority:** P1 — Owner workflow efficiency
**Points:** 13
**Branch:** `sortinghistory-bugs/main` (worker changes on `SortingHistory/feature/engagement-retention`)
**Created:** 2026-03-20
**Principle:** The owner should be able to review a fix, approve it, and have a testable build on his phone — all without ever opening GitHub or a terminal.

---

## Problem Statement

The bug pipeline generates fix PRs and sends a "PR Created" email, but the email is missing critical information and the approval flow stops short of a testable build. This forces the owner into GitHub for every fix — defeating the purpose of the automation.

Three specific failures from real usage (PR #165 fixing issue #163):

1. **The email does not show what changed.** The "Files Modified" section shows a count like `1` or a bare filename. The owner has no idea what code was added, removed, or altered. He must open GitHub, navigate to the PR, and read the diff manually. For a one-line fix like hiding the "New Game" button on Daily Challenge results, this is a 3-minute detour that should be zero.

2. **The email does not explain what the fix does.** The AI generated the fix and knows exactly what it did and why, but that explanation is not in the email. The QA summary (when present) focuses on test results, not on a plain-language description of the change. The owner has to reverse-engineer the intent from raw code.

3. **Approving the fix does not produce a testable build.** The current flow is: click "Review PR" (goes to GitHub) -> manually merge -> done. There is no build, no TestFlight upload. The owner still has to build locally or wait for someone to do it. The desired flow is: click "Approve & Deploy" in the email -> merge happens -> macOS runner builds the app -> IPA uploads to TestFlight -> owner gets a confirmation email with the build version and can test on device within ~15 minutes.

4. **Version string clobbering went undetected.** PR #165 changed the version string from `beta.20` to `alpha.22` via the `bump-version.sh` sed pattern (`1\.1\.0-alpha\.[0-9][0-9]*`), which does not match the `beta.XX` format the project switched to on 2026-03-14. Because the diff was not in the email, the owner could not have caught this before merging. If the diff had been visible, the `alpha.22` replacement of `beta.20` would have been immediately obvious.

---

## User Stories

**US-1:** As the pipeline owner, I want to see a plain-language summary of what the fix does in the PR email, so I can understand the change without reading code.

**US-2:** As the pipeline owner, I want to see the actual code diff (with file paths and line context) in the PR email, so I can review the fix without visiting GitHub.

**US-3:** As the pipeline owner, I want to see the original bug description in the email alongside the fix, so I can judge whether the fix actually addresses the reported problem.

**US-4:** As the pipeline owner, I want a "Review" button that builds and uploads to TestFlight (Empty Cup only) so I can test the fix on my phone, and then an "Approve" button to merge to main once I've confirmed the fix is correct — all from the same email without touching GitHub or a terminal.

**US-5:** As the pipeline owner, I want the version bump to use the correct version prefix (`beta.XX` not `alpha.XX`), so that version clobbering is impossible.

## Acceptance Criteria (numbered, testable)

### Part A: Email Content — Diff and Summary

**AC-1:** The PR email includes a "What This Fix Does" section containing a 1-3 sentence plain-language summary of the change, generated by the AI during the fix phase. This summary must reference the specific behavior changed (e.g., "Hides the 'New Game' button when viewing Daily Challenge results"), not generic text like "Fixed the bug."

**AC-2:** The PR email includes a "Code Changes" section showing the actual diff for each modified file. Each file's diff shows:
- The full file path (e.g., `Views/ResultsView.swift`)
- Added lines prefixed with `+` in green-tinted background
- Removed lines prefixed with `-` in red-tinted background
- Up to 3 lines of unchanged context above and below each hunk
- Line numbers for orientation

**AC-3:** If the total diff exceeds 200 lines (across all files), the email shows the first 200 lines with a note: "Diff truncated — [View full diff on GitHub](PR_URL/files)" linking to the PR files tab. This prevents email clients from clipping large emails.

**AC-4:** The diff is fetched from the GitHub API (`GET /repos/{owner}/{repo}/pulls/{pr_number}` with `Accept: application/vnd.github.v3.diff`) during the "Send PR created email" step of `sdk-bug-fix.yml`. The raw diff text is passed to `send-pr-email.ts` via an environment variable (`DIFF_FILE` pointing to a temp file) or piped through a file, NOT as a shell variable (diffs contain special characters that break shell expansion).

**AC-5:** The "What's The Bug" section (original issue body, already partially implemented) remains in the email and appears ABOVE the fix summary and diff, providing the context-then-fix reading order: Bug Description -> Fix Summary -> Code Diff -> QA Review -> Action Buttons.

**AC-6:** The version string row in the details table now shows the full version (e.g., `1.1.0-beta.21`) instead of just the alpha number. If the diff contains a SettingsView.swift change that modifies the version string, this is highlighted with a yellow background in the diff to draw attention.

### Part B: Review → Test → Approve/Rework/Reject Flow (Single Email)

The PR email contains FOUR buttons. All actions happen from this one email — no stages, no second email.

**Buttons (in order):**
1. **Review** → builds the app and uploads to TestFlight (Empty Cup internal group only) so the owner can test the fix on device
2. **Approve** → merges the PR to main (fix confirmed good after device testing)
3. **Rework** → closes the PR and re-triggers the fix pipeline (fix needs changes)
4. **Reject** → closes the PR and kills the issue (fix not wanted)

**Typical flow:** Owner reads diff in email → clicks Review → gets TestFlight build → tests on phone → comes back to same email → clicks Approve (good), Rework (not quite right), or Reject (don't want it).

**AC-7:** The PR email has four action buttons: Review (green), Approve (blue), Rework (amber), Reject (red). The existing "Fix Locally" button remains as a fifth option (gray).

**AC-8:** The **Review** button opens a confirmation page on `sortinghistory.com/api/pipeline/review-build` showing: issue number, PR number, fix summary preview, and a "Confirm: Build & Send to TestFlight" button. This does NOT merge the PR.

**AC-9:** On confirmation (POST), the worker dispatches a `repository_dispatch` event of type `review-build` to `sortinghistory-bugs`, with payload: `{ pr_number, issue_number, head_branch }`.

**AC-10:** A new GitHub Actions workflow `review-build.yml` in `sortinghistory-bugs` handles the `review-build` dispatch. It runs on `macos-14` and performs these steps in order:
1. Checkout private repo at the fix branch (NOT main — the PR is not merged yet)
2. Read `NEXT_BUILD_NUMBER`, bump version in SettingsView.swift (temporary, for this build only)
3. Archive the app (`xcodebuild archive`)
4. Export IPA (`xcodebuild -exportArchive`)
5. Upload to App Store Connect — targeting **Empty Cup internal testing group ONLY** (not Friends & Family, not public)
6. Send confirmation email with build version
7. Do NOT merge the PR. Do NOT push the version bump. The PR branch is unchanged.

**AC-11:** The workflow uses the App Store Connect API key already stored in the private repo (referenced in `memory/reference_appstore_api_key.md`). The key is passed to the runner via secrets: `APP_STORE_CONNECT_KEY_ID`, `APP_STORE_CONNECT_ISSUER_ID`, `APP_STORE_CONNECT_PRIVATE_KEY` (base64-encoded `.p8` file).

**AC-12:** The TestFlight upload targets the **"Empty Cup" internal testing group ONLY**. The `ExportOptions.plist` used for `xcodebuild -exportArchive` specifies `method: app-store` and `uploadBitcode: false`. The build MUST NOT be visible to Friends & Family or any external testers.

**AC-13:** After successful TestFlight upload, the workflow sends a confirmation email via Resend with:
- Green header: "TestFlight Build Ready for Review"
- Build version: `1.1.0-beta.XX`
- Issue number and title
- PR number
- Estimated availability: "~15-30 minutes for TestFlight processing"
- Reminder: "Come back to the original PR email to Approve, Rework, or Reject after testing."

**AC-14:** After successful TestFlight upload, the workflow adds the label `review-build-sent` to the issue and posts a comment: "Review build `1.1.0-beta.XX` uploaded to TestFlight (Empty Cup only). Test on device, then Approve/Rework/Reject from the PR email."

**AC-15:** The **Approve** button opens a confirmation page on `sortinghistory.com/api/pipeline/approve-merge`. On confirmation, it:
1. Rebases the fix branch against main
2. If conflict: abort, email owner with conflict details, stop
3. Squash-merges the PR to main
4. Bumps version with `NEXT_BUILD_NUMBER` (permanent this time), commits, pushes
5. Closes the issue with label `fixed`
6. Sends confirmation email: "Fix merged to main. Build `1.1.0-beta.XX` is the production version."

**AC-16:** If the build or upload fails during Review, the workflow sends a failure email with the error details and a "View Workflow Run" button. The PR remains open and unmerged.

**AC-17:** The **Rework** and **Reject** buttons work exactly as they do today (close PR, re-trigger or kill).

### Part C: Version Bump Fix

**AC-16:** `Scripts/bump-version.sh` is updated to match BOTH the `alpha.XX` and `beta.XX` version patterns. The sed replacement pattern changes from `1\.1\.0-alpha\.[0-9][0-9]*` to `1\.1\.0-\(alpha\|beta\)\.[0-9][0-9]*`. The replacement string uses the current version prefix from the file (detected before replacement), NOT a hardcoded `alpha`.

**AC-17:** The bump script detects the current prefix (`alpha` or `beta`) from the existing version string in SettingsView.swift and preserves it. If the file contains `1.1.0-beta.20`, the bump produces `1.1.0-beta.21`, never `1.1.0-alpha.21`.

## Technical Design

### 1. Diff Extraction (in `sdk-bug-fix.yml`)

Add a new step after PR creation and before the email step:

```yaml
- name: Fetch PR diff for email
  id: fetch-diff
  if: steps.create-pr.outputs.pr_url != ''
  env:
    GH_TOKEN: ${{ secrets.PRIVATE_REPO_PAT }}
  run: |
    PR_NUMBER="${{ steps.create-pr.outputs.pr_number }}"
    # Fetch unified diff from GitHub API
    gh api "repos/RaufGlasgow/Sorting-History/pulls/${PR_NUMBER}" \
      -H "Accept: application/vnd.github.v3.diff" \
      > /tmp/pr-diff.txt 2>/dev/null || echo "" > /tmp/pr-diff.txt

    # Also fetch AI fix summary from orchestrator output if available
    SUMMARY_FILE="${{ github.workspace }}/fix-summary.txt"
    if [ ! -f "$SUMMARY_FILE" ]; then
      echo "" > "$SUMMARY_FILE"
    fi
```

Pass to the email step:
```yaml
DIFF_FILE: /tmp/pr-diff.txt
FIX_SUMMARY_FILE: ${{ github.workspace }}/fix-summary.txt
```

### 2. Fix Summary Capture (in orchestrator)

The orchestrator already logs `[orchestrator] Bug fix result:`. Extend it to write a human-readable fix summary to `$GITHUB_WORKSPACE/fix-summary.txt`. This summary should be:
- Generated by the AI as part of the bug-fix subagent's final output
- 1-3 sentences describing WHAT changed and WHY
- Written to the file system (not just stdout) so the email step can read it

Add a new field to the orchestrator's output contract:
```
[orchestrator] Fix summary: <plain-language description>
```

Parse this in the YAML step alongside existing fields (compilation, confidence, etc.).

### 3. Email Template Changes (in `notification.ts`)

Extend `PRCreatedEmailInput`:
```typescript
export interface PRCreatedEmailInput {
  // ... existing fields ...
  /** Plain-language summary of what the fix does */
  fixSummary?: string;
  /** Raw unified diff text from GitHub API */
  diffText?: string;
}
```

New `buildDiffHtml()` function:
- Parse unified diff format into per-file hunks
- Render each hunk with:
  - File header in bold monospace
  - Added lines: `background: #e6ffec; color: #24292f`
  - Removed lines: `background: #ffebe9; color: #24292f`
  - Context lines: `background: #f6f8fa`
  - Line numbers in gray left gutter
- Truncate at 200 total diff lines across all files
- Use `<pre>` and `<code>` for monospace rendering (email-safe, no external CSS)
- Highlight SettingsView.swift version changes with yellow background

Email section order (updated):
1. Header (PR Ready badge)
2. Bug title + issue number
3. "What's The Bug" (existing issue body section)
4. **NEW: "What This Fix Does"** (fixSummary)
5. **NEW: "Code Changes"** (rendered diff)
6. QA Review (existing)
7. Details table (compilation, confidence, version — now full string)
8. Action buttons: **"Review"** (TestFlight build), **"Approve"** (merge to main), **"Rework"**, **"Reject"**, "Fix Locally"

### 4. Review-Build Endpoint (Cloudflare Worker)

Add `/api/pipeline/review-build` to the worker's router in `index.ts`:

- **GET:** Confirmation page showing issue number, PR number, fix summary preview, and "Confirm: Build & Send to TestFlight" button
- **POST:** Validate auth token, KV idempotency check (`review-build:{issueNum}`), dispatch `review-build` repository event to bugs repo with `{ pr_number, issue_number, head_branch }`

Add `/api/pipeline/approve-merge` to the worker's router:

- **GET:** Confirmation page showing issue number, PR number, and "Confirm: Merge to Main" button
- **POST:** Validate auth token, dispatch `approve-merge` repository event to bugs repo with `{ pr_number, issue_number }`

Reuse existing patterns from `handleMerge()` and `handlePipelineRedo()`.

### 5. Review-Build Workflow (`review-build.yml`)

```
jobs:

      - Send failure email with error details
```

### 5b. Approve-Merge Workflow (`approve-merge.yml`)

### 6. Version Bump Fix (`bump-version.sh`)

```bash
# Detect current prefix
CURRENT_PREFIX=$(grep -oE '1\.1\.0-(alpha|beta)\.' "$SETTINGS_FILE" | head -1 | sed 's/1\.1\.0-//' | sed 's/\.//')
if [ -z "$CURRENT_PREFIX" ]; then
  CURRENT_PREFIX="beta"  # default going forward
fi

# Replace with preserved prefix
if [[ "${OSTYPE:-}" == darwin* ]]; then
  sed -i '' "s/1\.1\.0-\(alpha\|beta\)\.[0-9][0-9]*/1.1.0-${CURRENT_PREFIX}.${CURRENT}/" "$SETTINGS_FILE"
else
  sed -i "s/1\.1\.0-\(alpha\|beta\)\.[0-9][0-9]*/1.1.0-${CURRENT_PREFIX}.${CURRENT}/" "$SETTINGS_FILE"
fi
```

### 7. Code Signing on CI

The `xcodebuild archive` step needs:
- **Signing certificate:** Distribution certificate (`.p12`) imported into the macOS runner's keychain from a base64-encoded secret
- **Provisioning profile:** App Store distribution profile installed to `~/Library/MobileDevice/Provisioning Profiles/`
- **ExportOptions.plist:** Committed to the repo (already exists at `build/ExportOptions.plist`) or generated dynamically

Standard pattern for GitHub Actions iOS builds:
```yaml
- name: Install signing certificate
  env:
    CERTIFICATE_BASE64: ${{ secrets.DISTRIBUTION_CERTIFICATE_BASE64 }}
    CERTIFICATE_PASSWORD: ${{ secrets.DISTRIBUTION_CERTIFICATE_PASSWORD }}
  run: |
    CERT_PATH=$RUNNER_TEMP/certificate.p12
    KEYCHAIN_PATH=$RUNNER_TEMP/app-signing.keychain-db
    echo -n "$CERTIFICATE_BASE64" | base64 --decode > $CERT_PATH
    security create-keychain -p "" $KEYCHAIN_PATH
    security set-keychain-settings -lut 21600 $KEYCHAIN_PATH
    security unlock-keychain -p "" $KEYCHAIN_PATH
    security import $CERT_PATH -P "$CERTIFICATE_PASSWORD" -A -t cert -f pkcs12 -k $KEYCHAIN_PATH
    security list-keychain -d user -s $KEYCHAIN_PATH
    security set-key-partition-list -S apple-tool:,apple: -k "" $KEYCHAIN_PATH

- name: Install provisioning profile
  env:
    PROFILE_BASE64: ${{ secrets.PROVISIONING_PROFILE_BASE64 }}
  run: |
    mkdir -p ~/Library/MobileDevice/Provisioning\ Profiles
    echo -n "$PROFILE_BASE64" | base64 --decode > ~/Library/MobileDevice/Provisioning\ Profiles/profile.mobileprovision
```

## Edge Cases

1. **Diff too large for email.** Some email clients (Gmail) clip messages over ~102KB. The 200-line truncation limit (AC-3) prevents this, but if individual lines are very long (e.g., JSON data files), the email could still be large. Mitigation: also enforce a 50KB cap on the diff HTML block; if exceeded, show only file names + line counts with a "View full diff" link.

2. **PR has merge conflicts at deploy time.** Between PR creation and the owner clicking "Approve & Deploy," someone may push to main. The rebase step in the workflow handles this — if it conflicts, the owner gets a conflict email (same as existing `rebase-and-merge.yml` behavior). No build is attempted.

3. **TestFlight upload fails due to signing.** Code signing on CI runners is notoriously fragile. The workflow must: (a) install cert + profile from secrets, (b) create a temporary keychain, (c) clean up the keychain after. If upload fails, the failure email includes the Xcode error output (last 50 lines).

4. **App Store Connect processing delay.** After upload, Apple takes 15-30 minutes to process the build. The confirmation email states this. The workflow does NOT wait for processing to complete — it confirms the upload was accepted.

5. **Double-click on Approve & Deploy.** KV idempotency in the Cloudflare Worker prevents duplicate dispatches (same pattern as existing `/merge` endpoint). Second click gets "Already Processed" page.

6. **Fix summary not available.** If the orchestrator does not write a fix summary (legacy runs, crashed mid-fix), the email shows the QA summary as fallback, or if that is also missing, shows "The pipeline generated a fix. Review the code changes below." Never show a blank section.

7. **Binary files in diff.** The GitHub diff API returns `Binary files differ` for non-text files (images, plists in binary format). The diff renderer should show "Binary file changed" instead of trying to render garbage.

8. **Email client does not render HTML well.** Some email clients strip `<pre>` formatting. Use inline styles on every element (already the pattern in the existing emails). Use `font-family: 'SF Mono', SFMono-Regular, Consolas, 'Liberation Mono', Menlo, monospace` for code blocks, with fallback to the system monospace.

9. **Concurrent deploys.** If two approve-deploy dispatches arrive simultaneously (shouldn't happen with KV idempotency, but defense in depth), the workflow uses a concurrency group `deploy-testflight` with `cancel-in-progress: false` so the first one completes.

10. **Version prefix migration.** If the project later changes from `beta` to `rc` or `release`, the bump script's regex needs updating. Document this in the script header.

## Out of Scope

- **Automated testing on device after TestFlight upload.** The owner tests manually. Automated UI testing on TestFlight builds is a separate future story.
- **Selective file diff.** The email shows the complete diff. Filtering to "only show Swift files" or "hide JSON changes" is not included.
- **PR review comments from email.** The owner cannot leave line-by-line review comments from the email. He can only approve (deploy) or reject (close PR). Detailed feedback requires the "Comment" or "Fix Locally" buttons.
- **Multi-PR batch deploys.** Each approve-deploy builds and uploads one PR at a time. Batching multiple fixes into a single TestFlight build is not included.
- **App Store submission.** TestFlight internal testing only. Submitting to App Store review is a manual step.
- **Rollback.** If a deployed build has a regression, the owner must revert the commit and re-deploy manually. Automated rollback is not included.
- **`CFBundleVersion` (build number) management.** The workflow bumps the marketing version string in SettingsView.swift. The `CFBundleVersion` in Info.plist may need separate handling for TestFlight (Apple requires it to increment). This is noted but not fully designed here — may need a companion AC.
